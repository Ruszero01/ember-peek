# 预览窗口的准备阶段与尺寸

状态：需求汇总（2026-09-23）。本文把关于"预览窗口尺寸"的诉求集中成一份可实现的规格：
**每条都是要求，不是对某个实现的描述**。实现方需要在同一次改动里更新相关文档、`sdk/README.md`
与 CHANGELOG（见 [CONTRIBUTING](../../CONTRIBUTING.md) 与 [AGENTS.md](../../AGENTS.md)）。

## 目标

看内容（图片、视频、PDF 页、PPT 页……）时，**窗口本身就是内容的形状**：内容从边到边铺满窗口，
没有上下或左右的留白，隐藏掉两条栏之后看起来就是一张"无边框"的画面。同时：

- 不是"按内容原始像素放大窗口"——大尺寸内容不该把窗口撑满整屏；
- 尺寸由内容决定，位置永远由用户/宿主决定；
- 用户自己调整窗口尺寸的意愿不被插件覆盖。

## 行为要求

### 1. 窗口在显示之前就定好尺寸

从隐藏状态打开时，尺寸调整必须发生在**窗口显示之前**，不允许"先以默认尺寸出现、再在用户眼前跳成内容的形状"。预览窗口已经显示而用户切换文件或视图时，新插件的首次声明应立即调整现有窗口；此时窗口位置仍保持不变。

因此需要一次**准备阶段**：宿主把预览窗口按"用户记住的尺寸"建好但**不显示**，插件的视图在这时
声明需要多大的窗口（或声明它没有要声明的东西），宿主拿到后设置窗口、**然后**才显示。

- 宿主在窗口启动时检查有没有声明：没有声明（或插件直接汇报就绪）就按用户记住的尺寸显示。
- 宿主必须有兜底：插件既不声明也不汇报就绪时，等待一小段时间后照常显示，不能把窗口永久留在隐藏状态。
- 准备阶段必须在用户看到窗口之前结束，所以插件在这里做的事要便宜（读文件头、问自己的原生进程），
  不要在这里解码整份内容。

### 2. 尺寸可以变，位置不可以

- **窗口位置由宿主提供稳定来源**：用户放过的位置就是那个位置；从未放过则由宿主居中。
- **插件只能影响尺寸，永远不能改变位置**：声明尺寸、宿主设置窗口之后，窗口的左上角不发生位移，
  也不因为换内容而"乱跑"。
- 尺寸变化不做位置补偿（不重新居中、不按比例挪动）。

### 3. 插件声明的尺寸是临时尺寸，不被持久化

宿主持久化的是**用户自己的**窗口尺寸与位置（拖动/缩放产生的那一份），插件声明的尺寸只是这次打开
的临时尺寸。

反面例子（必须避免）：先预览一张竖图（窗口被适配成窄的，例如 200 宽），再预览一张横图 ——
窗口却**被锁在 200 宽**。原因就是插件引起的尺寸变化被当成了用户的尺寸记录下来。

要求：

- 插件适配的基准是**用户记住的那一份固定尺寸**，不是"窗口当前碰巧是多少"。
- 插件声明的尺寸不写进用户记录；用户记录只被用户自己的操作改写。
- 用户随后自己调整窗口大小，那是用户的新尺寸，应被记录，并成为下一次适配的基准。

### 4. 尺寸从用户记住的那一份算起

适配必须可复现、不漂移：给定用户记住的窗口尺寸与内容的宽高比，结果唯一。规则（按最长边对齐）：

- 横内容（宽 ≥ 高，含正方形）：以**视口当前的宽度**为准，高度按比例算出；
- 竖内容：以**视口当前的高度**为准，宽度按比例算出；
- 另一边跟着算；这是插件声明尺寸的基准。宿主随后可能为了最小宽度等比增高窗口，最终高度仍受显示器工作区约束（见第 6 条）。

实现方可以把这条规则放在插件侧（插件自己算完声明最终尺寸）或宿主侧（插件只声明宽高比），
但必须只有一处负责，并且写清楚；无论放在哪侧，都要保证第 3 条的基准是"用户记住的尺寸"。

### 5. 插件需要读到"用户记住的窗口尺寸"

视图看不到自己所在的窗口有多大（它只知道自己那块矩形），所以宿主必须把这个数交给插件；
插件还需要知道宿主画在窗口里、不属于自己的部分（例如普通模式下的两条栏），才能把
"视口应当多大"换算成"窗口应当多大"。

### 6. 宿主只约束，不选择

宿主对声明的尺寸只做收敛，不做业务判断：

- 装不下显示器工作区：按**同一比例**缩小两个方向（保持形状），不因为一个方向超出就把形状拉变形；
- 低于预览窗口最小尺寸（320×240 CSS px）：先把宽、高按同一比例放大到两条下限都满足；如果因此超出显示器工作区，对超出的方向封顶，插件把图片居中装入窗口，允许留白但不裁切。窄长图优先增高，宽扁图优先增宽；设置窗口仍使用原有下限；
- 其余情况照声明执行。

### 7. 一个通用接口，不限于尺寸

这是插件与宿主之间的**准备阶段**：今天是"窗口尺寸"，将来同类"显示前就该知道的事实"（视频帧尺寸、
PDF 首页尺寸、播放器需要的浮层位置……）应能沿同一处扩展，宿主在这里只搬运、不解释内容语义。

- 载荷要可扩展（今天的字段是窗口尺寸，未知字段被忽略而不是报错）；
- 参与与否由插件声明（清单字段），没声明的插件维持现状：窗口照旧立即显示；
- 这是通用能力，不是图片专用。

### 8. 显示之后的呈现规则（图片与视频预览）

- 内容与窗口同形状时：内容铺满窗口（取两个比例中较大的那个，抹掉整数取整可能留下的 1px 缝）。
- 形状不成立时（例如被最小窗口抬过、或用户自己调过窗口）：内容**适应窗口**居中显示（留白但不裁切），
  不允许拉伸变形。沉浸模式的适应比例用整个视口计算，不扣浮动栏安全距离、不留固定横向边距，
  必要时放大小图，让图片在不裁切的前提下贴住窗口的限制边；普通模式继续照顾栏内安全距离。
- 用户缩放/平移之后，呈现归用户，不因为设置变化或窗口尺寸变化被重置。
- 视频没有图片缩放/平移操作：画面与视口同形状时铺满，形状被约束或用户拖动改变时用 `contain` 完整居中；元数据未知时保留原窗口并在可用后声明，宿主等待仍有上限。

### 9. 用户可见的开关

这是一个**设置项**，不是工具栏按钮：行为属于"打开时要什么样"，窗口本来就以某个尺寸打开，
再要求用户为同一件事按一次按钮没有意义。

- 图片与视频插件各自声明 `frameWindow`（"窗口对齐图片/视频"），默认开，跟着宿主持久化；
- 设置页里改它只影响下一次打开（已经显示的窗口不因此改变大小）；图片呈现方式对当前会话可以立即生效。

### 10. 既有要求（保持）

预览窗口的位置与大小记忆：位置来自用户、尺寸来自用户、最大化单独记为标志位、显示器变化后不留在
看不见的地方、托盘"重置为首次启动"一并忘记。详见 [Windows 桌面](../windows-desktop.md)。

## 性能与工程质量要求

- 准备阶段必须在用户可感知的延迟内结束：拿尺寸走便宜路径（文件头、插件自己的原生进程），
  不要为了这一次握手去解码内容或启动额外进程/页面。
- 不要为准备阶段新增一次页面加载或一个独立的入口文档；需要的话由插件自己把准备代码放在
  视图启动的最前面（轻量模块），但那是插件的选择，不是宿主的要求。
- 宿主侧的等待必须有上限，且上限只用于"插件卡住"这种情况。
- 宿主的状态锁与窗口 API 的关系必须写清楚：**窗口/监视器 API 由主线程应答，而主线程会在窗口事件
  回调里拿同一把锁**，所以任何线程持锁期间调用窗口 API 都会死锁（症状：预览一次就整机卡死，
  连前端轮询也一起停）。这条要作为注释写在宿主状态结构上。

## 当前工作区状态（便于接着做或重做）

工作区里已有一版未提交的实现（分支 `dev`），仅供参照，不构成规格：

- 宿主：`src-tauri/src/framing.rs`（尺寸收敛）、`src-tauri/src/desktop.rs`（准备阶段、窗口持有、
  位置与尺寸记忆、`Inner` 上的锁规则）、`src-tauri/src/main.rs`（`prepare_view` 命令）、
  `src/PluginView.tsx`（把视图的声明转给原生层，并把窗口尺寸交给视图）。
- 运行时与协议：`crates/runtime/src/manifest.rs`（清单字段 `prepare` 与其校验）、
  `SessionInfo.prepare`、`sdk/web/index.js`（`prepare(facts)`、`hostWindow()`）。
- 插件：`plugins/image/plugin.json`（`prepare: true`、设置项 `frameWindow`）、
  `plugins/image/ui/view.js`（按最长边适配、声明、铺满/适应）、
  `plugins/image/native/src/main.rs`（图片头解析：PNG/JPEG/GIF/BMP/WebP/AVIF/SVG，只读文件头）。

已知问题与边界：

- 曾经出现过"预览一次直接卡死"：持锁期间调用窗口 API 造成死锁（见上面「性能与工程质量要求」最后一条），
  已按该规则修复，但**修复后没有在真机上验证过**（本机运行中的应用占着二进制，无法重新链接）。
- 原先宿主最小窗口 640×440 会让 976×4065 长截图在 814 高的窗口中只能显示成约 160 宽的居中图片。预览窗口现在采用 320×240 下限：过窄或过矮时先等比放大，超出显示器工作区则封顶对应方向，图片居中适应；设置窗口仍为 640×440。
- 普通模式（两条栏在流里）下"窗口"与"视口"不是同一个矩形：插件需要把两条栏的高度加回去，
  否则内容只能适应而不能铺满。

## 验收

自动化（仓库门禁，见 [测试与质量门禁](../testing.md)）：

- 清单字段的校验（只在有 `view` 时合法）；
- 尺寸收敛的纯函数单测：按比例缩小、抬到最小窗口、形状不再成立时如实回落；
- SDK 契约：准备请求以声明的内容发出，窗口尺寸随会话信息到达视图；
- 头解析：每种声明支持的格式都能报出尺寸，不是该格式的字节不被当作尺寸读。

手动（Windows 真机，见 [Windows 桌面](../windows-desktop.md) 的手动验收）：

1. 沉浸模式打开一张横图：窗口**第一次出现就**是图片形状，画面从边到边，无留白；打开竖图时宽度
   跟着高度收敛，窗口不会长成比屏幕还高。
2. 连续看一张竖图再一张横图：窗口不应一次比一次窄（临时尺寸不进入用户记录）。
   保持预览窗口可见时切换图片，也应立即变成新图片的形状。
3. 自己拖窗口改尺寸后隐藏再打开同一文件：不出现"插件把窗口掰回去"的观感；位置不移动。
4. 关掉设置项再打开图片：窗口保持用户自己的尺寸和位置。
5. 低于 320 宽的竖图或低于 240 高的横图：窗口先按比例放大；若超出显示器工作区，窗口留在工作区内，图片回落为居中适应，不拉伸。
6. 重启宿主：窗口回到用户上次的位置与尺寸；最大化状态、显示器变化、重置路径符合既有要求。
