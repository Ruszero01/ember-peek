# 开发独立预览插件

## 包结构

```text
plugin.json
bin/your-plugin.exe
bin/your-importer.dll     可选
ui/index.html
ui/view.js
ui/style.css
ui/sdk.js                 可选，复制 sdk/web/index.js
ui/boot.js                可选，宿主提供的启动看护与错误上报（生成插件会自动带上）
ui/sdk-ui.css 等共享文件   可选，由构建脚本按引用放进包
ui/vendor/<文件名>         可选，页面 import 的第三方库（一层，不分目录）
dependencies.json         可选，vendor 里每个库的来源记录
ui/engine.wasm            可选
```

第三方库自带：`ui/vendor/` 下的文件用相对路径 import（`./vendor/mp4box.all.js`），页面里没有裸名解析、没有 import map、也没有打包器，所以放进去的必须是**自身不再 import 别的包**的构建（通常是 `dist/` 下的自带打包版）。文件若还需要独立 worker 脚本，页面只允许 blob worker，得自己从 `Blob` 建一个。
从工坊生成并取过库的包会带一份 `dependencies.json`，记下包名、确切版本、源给出的 sha512 完整性、许可证文件名与文件对照；手写插件如果也 vendor 了库，建议照同样格式写一份，导出与分享时来源才是可追溯的。工坊的取库规则与页面运行契约见 `docs/specs/plugin-workshop-v1.md` 的《生成物标准》。

```json
{
  "api": 1,
  "id": "example.model",
  "name": "模型预览",
  "version": "1.0.0",
  "extensions": ["fbx"],
  "icon": "file-type",
  "executable": "bin/your-plugin.exe",
  "entry": "ui/index.html",
  "capabilities": ["view", "controls"],
  "provides": "example.model/1",
  "permissions": ["readFile", "readResources"],
  "settings": [
    {
      "key": "defaultZoom",
      "type": "number",
      "label": "默认缩放比例",
      "help": "打开模型时的初始缩放。",
      "default": 1,
      "min": 0.1,
      "max": 8,
      "step": 0.1
    }
  ],
  "i18n": {
    "en": {
      "name": "Model preview",
      "settings": {
        "defaultZoom": {
          "label": "Default zoom",
          "help": "Initial zoom when a model opens."
        }
      }
    }
  }
}
```

`api:1` 是当前唯一协议版本，没有旧版兼容入口：清单的 `view` 字段不再接受，入口统一为 `entry` + `capabilities`。`revision` 由安装器生成，市场构建额外生成 `buildId` 内容指纹。同一格式匹配所有已启用插件；`capabilities` 决定视口、浮层和功能气泡，其中 `view` 与 `overlay` 可以同时声明 —— 那是同一个 `entry` 挂载两次，用 `role` 区分。匹配什么文件由 `extensions`（不区分大小写；省略、`all` 或 `*` 表示全部）和 `fileNames`（精确文件名，用于 `Dockerfile`、`LICENSE` 这类文件）共同决定。**清单拒绝未知字段**：写错的键会让包加载失败并报出字段名，而不是被静默忽略。`version` 是**插件自己的版本**，不随宿主版本走：插件按自己的节奏发版，宿主升级不必带上它，插件修一行代码也不必动应用的版本号。各字段的取值与上限见 [能力协议](specs/plugin-capabilities.md) 的清单表，具体槽位规则见同一篇的后半部分。

`i18n` 是可选的语言表，键是语言标签（小写 BCP-47，最多 16 种），值是该语言的 `name` 与 `settings`（设置项的 `label`、`help`，以及 `select` 选项标签，按选项 `value` 索引）。它是**覆盖**而不是替换：某个字段没写就沿用清单里的声明，所以插件只写自己翻得了的部分。宿主按当前界面语言取值，`zh-CN` 找不到时退回 `zh`；插件不需要知道宿主支持哪些语言，宿主加一种语言也不需要插件跟版。不写 `i18n` 的插件在任何语言下都显示声明里的原文。

翻译和声明本身一样严格地校验，失败即整个包加载失败：语言标签形状、名称与说明的长度上限，以及**必须指向已声明的设置项和选项** —— 写错一个 key 会在扫描警告里明确报出来，而不是静默地少显示一段文案。

## 插件图标

`icon` 可选，填写宿主图标集里的名字（小写 kebab-case）。插件不打包图标资源：宿主自己提供图形，插件只声明用哪个。这样避免了路径校验、格式白名单、体积上限和内容哈希这一整套问题，也防止包把自己伪装成另一个。

可用名称：

```text
archive  binary  braces  code  file-code  file-json  file-pen
file-text  file-type  film  image  info  music  presentation  table
```

不填，或填宿主不认识的名字，都会退回通用图标 —— **不会导致加载失败**。因此宿主后续扩充图标集时，已发布的插件不会被作废。名字格式（小写）、长度上限 40 则会在加载时校验。

侧栏的“插件设置”入口、插件管理卡片和市场卡片共用同一个图标。

## 插件设置

`settings` 是可选数组。**宿主读取声明后自己画出设置界面**，每个插件在设置侧栏有独立入口，点进去就是该插件的设置页；插件不需要提供任何表单标记，用户改的值由宿主校验、持久化并下发。

```json
{
  "key": "wrap",
  "type": "bool",
  "label": "自动换行",
  "help": "关闭后长行横向滚动。",
  "default": true
}
```

公共字段：`key`（必填，`[A-Za-z0-9._-]`，≤64 字节，插件内唯一）、`type`（必填）、`label`（必填，≤80 字）、`help`（可选说明，≤400 字）、`default`（可选，缺省按下表推导）、`hidden`（可选，`true` 时宿主照常校验与持久化，但**不画控件**）。每个插件最多 32 项。

| `type` | 界面控件 | 专属字段 | 缺省 `default` |
|---|---|---|---|
| `bool` | 开关 | — | `false` |
| `number` | 数字输入 | `min` `max` `step` `suffix` `displayMultiplier` | `0` |
| `select` | 下拉选择 | `options: [{value,label}]`（必填，≤64 项） | 第一个选项 |
| `text` | 单行文本 | — | `""` |

`suffix`（≤8 字）和 `displayMultiplier`（有限正数）只改变**界面上怎么显示**一个数字项：界面显示 `值 × displayMultiplier` 再拼上 `suffix`，用户输入时先除掉倍率再存。所以插件拿到的永远是原值。例如插件内部用 `1.0` 表示 100%，声明 `displayMultiplier: 100` 与 `suffix: "%"`，设置页就显示成 `100%`，插件代码里不需要任何换算。

`hidden: true` 用于**插件自己的状态**：值照样按同一套规则校验、持久化、通过 `configuration()` 下发，也可以用 `setSetting()` 写回，但设置页不出现任何控件。音量、上次缩放倍数这类"用户调一次就该记住"的值用它，不必为一个数字在设置里多读一行；需要用户看见并主动选择的才声明成普通设置项（例如自动播放、循环播放）。

`default` 会按同一套规则校验并夹取，所以 `select` 的默认值必须是已声明的选项之一，数字项也会被对齐到 `step`。

校验发生在两处，都失败得明确而不是静默降级：

- **清单加载时**：`default` 必须满足自己的 schema；`select` 必须有 `options`；`options` 的 `value` 不能重复；**未知 `type` 会让整个插件加载失败并出现在设置页的警告里**。这样新插件在旧宿主上会显式报错，而不是被渲染成错误的控件。
- **写入时**：`number` 会被夹到 `[min,max]` 并对齐 `step`；`select` 只接受已声明的选项；未声明的 `key` 直接拒绝。

宿主只持久化**与默认值不同**的项。把某项改回默认值即删除该覆盖，因此插件后续调整默认值会自动生效，不需要迁移。清单里已删除的设置项，存储中的残留值会被忽略。

设置项的 `label`、`help` 与 `select` 选项名都是界面文案，可以按语言覆盖，见[包结构](#包结构)的 `i18n`。键（`key`）与取值永远不翻译：它们是宿主与插件之间的契约。

插件有两个面，都能拿到设置：

**原生进程**收到 `params.settings`，是按声明补全默认值后的完整对象。开启文件时随 `open` 下发：

```json
{"id":1,"method":"open","params":{"session":"s1","path":"C:\\a.png","settings":{"defaultZoom":1.5}}}
```

自定义方法同样携带 `settings`；`release` 仅包含会话 ID。用户改动时宿主会主动发 `settings` 通知，插件应回一个 result 表示接受；返回 error 会在宿主侧记录，但**已存储的值不会被回滚**，插件下次 `open` 仍会看到它。

```json
{"id":9,"method":"settings","params":{"session":"s1","settings":{"defaultZoom":2}}}
```

Rust 插件可用 `ember_plugin_sdk::{settings, setting, settings_applied}` 免去手工解析。`settings`、`open`、`release` 是生命周期方法，由插件实现响应，网页不得作为自定义 RPC 调用。

**插件网页**在 `ready` 的载荷里拿到 `settings`，也可以用 `configuration()` 随时读取、用 `onSettings(fn)` 响应变化：

```js
import { ready, configuration, onSettings } from './sdk.js';
const { data, settings } = await ready;   // settings 与 data 同时到达
const zoom = Number(configuration().defaultZoom);
onSettings(next => { /* 应用新值 */ });
```

设置变化只会送到**当前已存在的会话**。宿主不会因为设置改变而自动重开已经打开的文件，因此插件应当自行决定哪些项对当前会话立即生效（例如文本插件的换行和行号），哪些只影响后续打开的文件。图片插件用“用户是否已手动操作”来区分：未手动缩放或平移的会话会立即应用“默认适应窗口”，操作过的会话保持当前视图。

## 原生进程协议

宿主使用包目录作为工作目录，隐藏控制台，连接 stdin/stdout。每行一个 UTF-8 JSON 对象。stdout 只能用于协议，不能写调试日志。插件可以使用 Rust、C++、.NET 或其他能生成独立程序的语言；运行依赖必须包含在包内或由安装环境提供。

请求：

```json
{"id":1,"method":"open","params":{"session":"s1","path":"C:\\Models\\chair.fbx"}}
```

成功响应：

```json
{"id":1,"result":{"yourPluginData":"any JSON shape"}}
```

错误响应：

```json
{"id":1,"error":"模型解析失败"}
```

`result` 的结构完全由插件定义。原生进程可以保留会话自己的索引、网格或分页缓存；视图通过后续自定义方法按需取数据。

```json
{"id":2,"method":"mesh-chunk","params":{"session":"s1","path":"C:\\Models\\chair.fbx","value":{"mesh":4}}}
```

会话回收时，如果进程还有其他会话，宿主发 `release` 和会话 ID。没有任何会话时直接终止进程。需要保留原生状态的插件应实现 `release` 清理；示例 SDK 对无状态插件默认返回 null。请求可以并发，响应必须回显正确 ID，禁止依赖响应顺序。

进程崩溃会令未完成请求失败，后续请求可启动新进程，但宿主不会猜测并恢复插件内部缓存。使用原生会话状态的插件，应能够根据请求中的 `session` 和 `path` 重建所需状态，或返回明确错误要求重新打开文件。

## 插件网页

完整导出清单、兼容规则与视图 SDK / 工具 SDK 的边界见 [SDK contracts](../sdk/README.md)。

```js
import {
  ready, controls, call, read, status, presented, onVisibility,
  fileUrl, streamUrl, fileBlob, resourceUrl, resourceBlob,
  setSetting, panel, postTo, onMessage,
} from './sdk.js';
const {data, file, role} = await ready;   // role 是 'view' 或 'panel'

// 同时声明 view + overlay 时，同一个 entry 会被挂载两次，用 role 决定这次画什么：
// 主视口画正文，浮层画功能操作区。
if (role === 'panel') renderPanel(data); else renderView(data);

// 在这里创建自己的渲染器，例如 Three.js、PDF.js、Canvas 或普通 DOM。
// data 是原生 open 的 result，file 只有 name 和 size。
controls([
  {id:'orbit',kind:'button',label:'环绕模型',icon:'fit',run() { /* 插件处理 */ }},
  {id:'grid',kind:'toggle',label:'显示网格',icon:'actual',active:true,run() { /* 插件处理 */ }},
  {id:'find',kind:'button',label:'搜索图层',icon:'search',
   run() { /* 打开自己的浮层 */ panel(true); }},
]);

// 两个挂载是两个文档，彼此看不见，所以插件内部通信走宿主这根不透明管道：
// 宿主只转发，不解析。谁拥有状态由插件自己决定。
if (role === 'panel')
  onMessage(payload => { if (payload.kind === 'status') showCount(payload.count); });
else
  postTo('panel', {kind: 'status', count: 17});   // 浮层没开时返回 false，不报错

const mesh = await call('mesh-chunk', {mesh:4});
const firstBytes = await read(0, 65536);
status('模型已加载');
await presented(); // 首次解析、解码与视图初始化真正完成后发送。
onVisibility(visible => { /* 暂停或恢复插件渲染循环 */ });
```

`ready` 表示与宿主建立连接并收到原生数据；`presented()` 表示插件自己的视图已经可用。初始化期间切换到其他类型不会回收这个会话。初始化失败调用 `presented(errorMessage)`；未完成视图在 120 秒后明确报错，避免损坏的插件永久占用缓存。次要挂载（浮层）不能调用 `presented()`。

### 控件

| `kind` | 宿主行为 | 专属字段 |
|---|---|---|
| `button` | 点击时回调插件 | — |
| `toggle` | 画成可点亮的按钮，并反映状态 | `active: true` 表示点亮 |

控件对宿主是不透明的：它只负责聚焦插件、把控件 id 转发回去。插件想用这个按钮打开自己的浮层、切换模式还是弹别的东西，都由插件决定。

**这些界面各自有归属槽位，视口里只放渲染内容和样式**：一行状态（文件名、大小、分辨率、进度）给左下角信息栏（`status()`）；结构化或持续更新的统计、需要持续操作的控件（拖动进度条、音量、取色器）做成语义浮层，由工具栏上的一个控件开关（`panel()`）；工具按钮一律进右下角工具栏。把进度条、按钮或自绘的"沉浸"浮层做进视口，等于在视口里重新实现一遍宿主已经负责的显隐与浮层位置，插件 UI 也会和宿主割裂——完整规则见 [插件能力、共享源与槽位协议](specs/plugin-capabilities.md) 的「界面归属」一节，其中也说明了**「沉浸」不是插件要实现的功能，不该出现在插件描述里**。

图标可用 `search/check/copy/plus/minus/fit/actual/up/down/text-wrap/save/rotate-ccw/hash/code`，未知名称显示通用功能图标（与插件图标一样，写错不会导致加载失败）。控件最多 16 个。

`active` 只有显式 `true` 才算点亮，其他值一律视为关闭——这样写错的声明不会让控件被误点亮。

### 搜索这类功能由插件自己做

宿主不认识"搜索"：没有搜索框组件，也没有 `kind: 'search'` 控件。要做搜索的插件按自己的需要组合三样东西：

1. 一个 `button` 控件，点击时用 `panel(true)` 打开自己的浮层；**打开浮层的控件应该声明成 `kind: 'toggle'` 并让 `active` 跟随浮层开关状态**，宿主会把打开中的按钮点亮，和「自动换行」是同一套状态语言；用普通 `button` 就丢掉了这个状态。浮层自己关闭时（✕、Esc）要用内部消息告诉视口，否则按钮会和实际显示不一致；
2. 浮层里调用 `mountSearchBar()`（来自随包分发的 `sdk-search.js`）：输入框、上一个/下一个、`n/m` 计数、Enter/Shift+Enter、Esc 关闭都由它提供，外观与宿主控件一致；
3. 匹配算法在插件里，`findOccurrences(text, query)` 给出全部 `[start, end)` 位置；高亮不要自己画，交给共享文本视图（见下）。

**同一个功能不要写第二遍。** 共享组件是插件侧代码：`npm run plugins:build` 会按插件实际引用到的部分把它和 `sdk.js` 一起放进包，并参与 `buildId` 计算，所以改共享组件会重新发布用到它的插件。**只有真正引用它的插件才会带上它**：没有浮层的插件包里不会多出搜索条，没有正文视口的包里也不会多出文本组件。文本编辑插件用的就是这个搜索条。

浮层和主视口是两个文档，插件内部要传状态就用 `postTo(role, payload)` / `onMessage(fn)`，宿主只转发不解析，`postTo` 返回对端是否挂载（浮层没开时是 `false`，不是错误）。通常由主视口持有匹配集，浮层只显示结果。

导航不经过插件的原生进程，因此不占用 `plugin_call` 的并发额度。

**高亮和跳转不要自己实现**：共享文本视图（`createTextView` 的返回值）已经把这两件事做完了，另写一套只会和字体度量、折行模式打架。

- `surface.search(query)` 用 CodeMirror 装饰给**命中的字符**着色。别整行点亮：那看不出命中在行内哪个位置，也分不清相邻命中。折行与非折行两种布局由视图自己处理。
- `surface.select(from, to)` 选中并滚动到命中。不要自己按行号算 `scrollTop`：折行模式没有固定行高网格，虚拟化布局下目标行还可能尚未生成，视图内部已经按正确顺序处理。
- 浮层里的输入框必须独占焦点（不给它焦点，用户打第二个字就断了），所以搜索条只通过 `postTo` 把查询和当前命中序号发给视口，高亮与滚动留在视口这一侧。超大文本可以只报计数不做选中，但不要另写一层镜像文本去对字体度量。

### 界面语言

宿主解析界面语言（设置里的“跟随系统”用的是窗口看到的系统偏好），并把它推给每个插件网页：`init` 载荷带 `locale`，用户改语言时再发一条 `locale` 消息。插件侧用 SDK 的三个函数接入：

```js
import { locale, onLocale, translate } from './sdk.js';

const say = translate({
  'zh-CN': { copy: '复制文本', lines: '共 {count} 行' },
  en:      { copy: 'Copy text', lines: '{count} lines' },
});
say('copy');                  // 当前语言的文案
say('lines', { count: 12 });  // {name} 占位符会被填上
onLocale(() => publishControls());   // 语言变了：重新发布带文案的工具栏控件
```

取值顺序是当前标签 → 去掉地区的语言（`zh-CN` → `zh`）→ `en` → key 本身。所以插件**只需要提供自己会的语言**：缺的部分既不会显示成空白，也不会让宿主拒绝这个包。控件标签、状态行、浮层文案都属于插件自己的界面，宿主不认识，也就不可能替它翻译。

声明在清单里的文案（`name`、设置项 `label`/`help`）不走这条通道：那些由宿主绘制，写在 `plugin.json` 的 `i18n` 里（见[包结构](#包结构)）。两者是同一件事的两半 —— 宿主画的宿主翻，插件画的插件翻。

语言可以在任何时候切换，所以插件要重新送出**已经显示出去**的文字，而不只是下次绘制的：工具栏控件的标签、状态行、自己画在浮层或窗格里的文案，以及给屏幕阅读器用的 `aria-label`。共享组件已经这么做了（`sdk-view.js` 的字面标签、`mountSearchBar` 的按钮都是随语言重建的），插件自己要记住的是：**任何一次性写入 DOM 的文案，都要在 `onLocale` 里再写一遍**。文件信息插件是个现成例子——它把 `render()` 挂在 `onLocale` 上，面板标签跟着语言变。

已经显示出来的**错误文本**是例外：那是那一刻发生的事，宿主也不认识它的内容，所以它会保持当时的语言，直到下一次事件刷新它。

`document.documentElement.lang` 由 SDK 跟着当前语言设置，插件不用自己管。

### 写设置

`setSetting(key, value)` 让视图代用户改一个已声明的设置项（例如工具栏上的「自动换行」开关）。宿主按清单校验并持久化，随后照常通过 `onSettings` 回报结果——所以工具栏开关和设置页永远一致。

宿主会把当前主题写成 CSS 变量注入插件文档，**完整清单就是这些，没有别的**：

```text
颜色  --bg --canvas --panel --card --raised --hover
      --border --text --muted --faint --accent --accent-bg
      --color-scheme（dark / light）
形状  --radius-control --radius-pill --radius-card
      --control-h --control-h-sm --space-1..4 --field-label-w
字体  --font-ui --font-mono --mono-size --mono-leading
```

`--color-scheme` 不是画什么颜色，而是告诉平台**它自己画的那部分**该用哪套：插件文档的滚动条、原生 `<select>` 弹出的列表、自动填充的底色。SDK 收到主题时会把它设到 `documentElement.style.colorScheme` 上，浅色窗口里的深色下拉列表就是这么来的。

浅色与深色下同一组变量取不同值，随主题切换实时更新。加上这些形状与字体变量之后，**换肤不再只是换配色**：圆角、控件高度、间距、字体全部跟着走，凡是用了共享组件的插件都不用改代码。

**给 `var()` 写兜底值时要注意**：它会长期生效，所以颜色兜底必须是中性或透明的，不要写死某一种主题的颜色 —— 否则浅色窗口里会出现深色块。`--hover`（控件悬停底色）和 `--raised`（浮起的表面）最容易漏。

网页里还要 `<link rel="stylesheet" href="./sdk-ui.css">`：它既是共享组件库的样式，也提供与宿主一致的滚动条外观。插件网页是独立文档，**不链这份样式表就会露出平台默认滚动条**（浅色、带箭头、不随主题变化），在深色浮层里非常突兀。

### 共享组件库

`sdk-ui.css` 里现成的东西（都是宿主 token 驱动的）：

| 组件 | 用法 |
|---|---|
| `.ui-button` / `.ui-button.primary` / `.ui-button.on` | 普通、主操作、点亮态（`on` 与宿主工具栏同一个词） |
| `.ui-icon-button` / `.ui-icon-button.on` | 纯图标按钮 |
| `.ui-input` | 单行输入框，含焦点描边 |
| `.ui-select` | 下拉选择：`<span class="ui-select"><select>…</select></span>`。列表也按 token 绘制，不是平台默认那份；键盘、首字母跳转和无障碍树仍由浏览器负责 |
| `.ui-fields` | 标签/取值列表（`dl > dt + dd`），文件信息面板就是它 |
| `.search-bar` + `mountSearchBar()`（`sdk-search.js`） | 搜索条：输入框、上一个/下一个、`n/m`、Enter/Shift+Enter、Esc |
| 滚动条 | 全局，链上样式表就有 |

**规则：优先用库里的组件。** 库里没有的，就用同一套 token 自己写，不要另造数值 —— 这样换肤时它照样跟着走。同一个实现只能有一份：库里已有的组件不要复制出来改，复制的那份迟早会和库里那份脱节，而脱节的表现通常是深色浮层里露出白色默认滚动条这种细节。

共享实现怎么进包，以及包内该 import 哪个名字：

| 包内文件 | 来源 | 进包方式 |
|---|---|---|
| `ui/sdk.js` | `sdk/web/index.js` | 原样复制，每个包都有 |
| `ui/sdk-ui.css`、`ui/sdk-search.js`、`ui/sdk-text.css` | `sdk/web/ui.css`、`sdk/web/search.js`、`sdk/web/text/surface.css` | 插件引用了才复制 |
| `ui/sdk-view.js`、`ui/sdk-navigation.js`、`ui/sdk-markdown.js` | `sdk/web/text/` 下的同名模块 | 插件引用了才由 esbuild 打包，依赖（含 `gutter.js` 与 CodeMirror 等第三方库）一并进包 |

所以插件源码里的 `./sdk-view.js` 对应的是包内文件，开发时由构建脚本生成；`sdk/web/text/view.js` 内部的相对导入（例如 `../gutter.js`）插件不用管，打包器会处理。表里这些文件都参与 `buildId`，改一次就会重新发布用到它的插件。

### 文本类视口的留白标准

正文类视口（文本、代码、Markdown、编辑，以及以后任何显示文档正文的插件）共用一套留白，折行与不折行都一样。三个预览和编辑器导入的是同一份 `sdk-view.js`，所以这套留白改在共享组件里，不要在某个插件里覆盖 —— 一处改动就该影响所有正文视口。

- **横向留白加在行那一层，不要加在滚动容器上。** 共享视图给每行 `padding: 0 24px 0 16px`：右边比左边多出的 8px 是滚动条道，正好等于 kit 里 `::-webkit-scrollbar` 的宽度。少了这一道，不折行时长行会一直排到内容框右缘、顶着甚至钻到滚动条下面；折行时又看不出问题，于是症状表现得像"留白只在不折行时消失"。
- **上下留白用宿主安全距离。** `--safe-top` / `--safe-bottom` 由主题通道下发，共享视图把它加在 `.cm-content` 的纵向内边距上，同时以 `EditorView.scrollMargins` 计入滚动边界，所以跳到首行/末行不会被浮动栏压住。沉浸模式下它已经包含浮动栏高度，普通模式只有 6px 缓冲；插件不要再自己加标题栏或功能栏高度。
- **滚动容器铺满视口。** 页面壳是 `sdk-text.css` 里的 `#surface { flex: 1; min-height: 0; overflow: hidden }`，滚动条由 CodeMirror 的 `.cm-scroller` 画在视口边缘。滚动条永远贴着自己所属盒子的边缘，所以内边距加在外层容器上会把滚动条一起推进来，那时它就不在视口边缘了。

Markdown 的渲染视图不是 CodeMirror：它的滚动容器就是 `#rendered` 本身，留白写在它自己的 `padding` 上，安全距离用同一组变量；切到源码视图时仍走共享文本视图，两边的字体与行高保持一致。

### 主视口同一时刻只有一个网页

主视口像显示器的输入源：只有当前视口插件的网页是挂载着的，切换到另一个插件就会把上一个卸载，它下一次被切回来时重新初始化。所以**视口网页不要依赖自己一直活着**：滚动位置、缩放这类只存在于网页里的状态，切走再回来会丢；插件网页运行在不透明源里（`sandbox="allow-scripts"`，没有 localStorage），也没法自己存。需要跨切换保留的状态请交给宿主：声明成设置项，或让原生进程持有。

唯一的例外是声明了未提交变更的会话：它的网页必须留着，因为变更只存在于那个网页里，卸载就等于丢数据。变更一解除（保存或撤销后调用 `pending(false)`），它就和普通视口一样可以被卸载。

浮层与主视口互不影响：浮层只在自己打开时挂载。

页面脚本必须作为包内 JS 文件引用；模块、CSS、WASM 等资源通过相对路径加载。单个静态资源最多 32 MiB。禁止内联 JS 与网络脚本，第三方渲染库应打包进插件。插件完全控制页面；不要引用宿主 `src` 或依赖宿主 React 组件 —— **这条现在由打包步骤强制**（见[安装与验收](#安装与验收)）。

通用 `read(offset, length)` 每次最多 1 MiB，只能读当前会话文件，且需要 `readFile` 权限。同一份文件还有三个入口：`fileUrl()` 返回经权限校验的整文件 URL（适合让浏览器直接解码 32 MiB 以内的图片等内容），`streamUrl()` 提供不带格式语义的分段 URL，让支持 HTTP Range 的浏览器原生消费者按需读取大型文件并尽早呈现，`fileBlob(size, type)` 才会把整份文件复制成 `Blob`。不要为了方便一律使用 `fileBlob()`；首屏只需要少量字节或文件可能很大时应优先选择流式入口。宿主只负责权限和有界字节段，不解释读取方是视频、音频还是其它解析器。

文档里引用的关联资源使用独立的 `readResources` 权限。插件解析格式并把原始引用交给 `resourceUrl(reference)` 或 `resourceBlob(reference)`：相对路径以当前文档所在目录为基准，支持 `../`、绝对路径和 `file:` URL；公开的 HTTP(S) 地址由宿主中介下载，逐跳校验重定向并拒绝本机、内网、链路本地地址。`<img>` 可直接使用 `resourceUrl()`，媒体、字体、WASM 或需要字节输入的解析器使用 `resourceBlob()`，再按需创建 `blob:` URL。关联资源单项最多 64 MiB。宿主只负责通用寻址、权限、网络和字节传输，不识别 Markdown、网页归档或其它具体格式；引用发现、类型处理和最终呈现仍由插件完成。

`clipboard(text)` 需要 `clipboard` 权限，且只有当前显示的视图能用。涉及原生解析结果的大数据应分页或分块，不要将大型模型塞进单个 JSON 响应。

## 安装与验收

设置窗口的“插件”页分两个标签：**插件市场**负责找和装（未安装的插件是完整卡片，已安装的只列成小卡片，带更新按钮），**插件管理**负责已安装插件的启用、排序与卸载；两个标签共用的工具栏里还有“从目录安装”，用于安装一个已构建的包目录。构建脚本扫描仓库 `plugins`，每个插件源码目录还需提供 `listing.json`，包含 `summary`、`publisher`，以及可选的 `recommended`（见下：首启引导页只列出标了它的插件）。生成的市场目录与 `.plugins` 安装目录相互独立。添加新条目不需要修改宿主支持列表。

`npm run dev` 包含市场首次构建、前端服务、Tauri 后端监视和插件监视。插件修改后市场版本更新，开发宿主同步已安装的市场插件；卸载的插件不会被监视器自动重新安装。

**打包前会检查每个插件是不是自足的包**，三类问题都直接让构建失败，而不是发出一个装到用户机器上才暴露的包：

1. **页面引用**：插件网页引用的每个文件（JS 的 import、HTML 的 `src`/`href`、CSS 的 `@import` 与 `url()`）必须是插件自己 `ui/` 里的，或随包分发的 SDK 文件。指向宿主源码、绝对路径与网络地址都被拒绝，写错文件名也一样——包里的网页是原样复制的，这类错误原本只会表现成“插件视图未建立连接”。`data:` 内联资源不受影响。
2. **native 依赖**：插件的原生 crate 只能按路径依赖 `sdk/native` 与 `crates/text-document`，不能依赖宿主运行时或仓库里的其它 crate。宿主与插件同在一个仓库，这是唯一能真正拦住“插件偷偷依赖宿主”的地方。
3. **版本一致**：`plugin.json` 的 `version` 必须与插件 native crate 自己声明的 `version` 相同；用 `version.workspace = true` 继承应用版本会被拒绝，因为那等于把插件版本重新绑回应用版本。

**更新是覆盖式的，每个插件在磁盘上只有一个目录。** 更新时先停掉该插件的原生进程（Windows 上目录里有正在运行的 exe 就既改不了名也删不掉），然后把新包换进去：

1. 新包先整棵复制到暂存目录并确认能加载，此时还没有动过已安装的那个目录；
2. 已安装目录改名到 `.replaced-<目录名>`，暂存目录改名就位，最后删掉改名到一边的那份——两步都是单次改名，中间崩溃的话下次 `scan` 会把 `.replaced-` 那份改回来，最坏结果是“还是旧版本”，不会是“半个新版本”；
3. 重新组合被切断的预览。

不做逐个文件往活目录里写：那样的复制不是原子的，中途崩溃、磁盘写满或被杀毒拦下都会留下新旧混装的安装（新 exe 配旧 ui，或者截断的 exe），而且要等下次用到插件才暴露。安装目录名里的 `revision` 保持不变，所以路径在一次安装的生命周期里是稳定的；`scan` 只认一个修订，发现同一插件存在多余目录（例如旧方案留下的）会把它们按卸载同一条路径退休掉。

**正在预览的会被切断并自动恢复。** 插件进程是多个文件共用的，所以更新会停掉整个插件、丢掉它与同一批文件里的会话，换装完成后立刻按原路径重新打开这些文件——用户看到的是预览自己刷新了一下，窗口仍停在同一文件、同一插件上，查看位置由宿主的 `view_states` 找回。恢复失败（新构建不再认这个扩展名、或启动就报错）时，窗口回到“即刻一览”空状态，可以重新打开文件。

**有未提交变更时更新被拒绝。** 插件通过 `pending()` 声明手上的变更，宿主检查全部受影响会话，包括同文件的其他插件，以及共享进程服务的其他文件。检查与会话接管在同一锁内完成，避免为了换装丢掉用户没保存的内容。下载缓存只保留磁盘上在用构建对应的包，卸载后对应条目一并清掉。

新增格式验收应满足：空宿主打不开该格式；安装包后能打开；禁用后新的打开请求失败；慢加载期间切换到其他插件后能再切回来；闲置后进程退出；重新打开可以重建。FBX/PDF/PSD 需要在插件包内真正实现相应解析与渲染，当前基线不含这些格式，也不会假装支持。

## 激活与气泡交互

清单可声明 `"activation": { "mode": "auto", "priority": 100 }`。省略时为 auto、0；manual 表示点击气泡进入。清单优先级越大越靠前；用户通过左侧插件列表拖动排序（越靠上越优先），右侧使用“自动激活”开关，不显示数字优先级。没有自动进入的视口时回退到手动视口；激活规则不取消任何后台初始化。设置变化从下一次打开文件生效。

气泡名称就是视口入口，控件操作会先聚焦所属插件。**功能栏同一时刻只有当前插件的按钮是展开的**：其余气泡收成一条名称，切换视口时以宽度动效过渡。所以插件不需要考虑"我的按钮会不会挤到别人"，也不必自己创建宿主视口切换器。编辑类插件可在保存成功、解除 `pending` 后调用 `fileChanged({returnToSource:true})` 刷新并返回自动视口；普通 `fileChanged()` 保持当前插件。没有修改时使用 `returnView()`。这两个桥接口不替插件保存内容；调用失败时插件必须继续保留自己的变更声明。只有一个视口时仍留在该视口。

文本、代码、Markdown 预览与文本编辑都提供 `ember.text/1`，同时安装时只选一个解析源，其余消费它的结果；编辑器也可独立安装。它们复用插件侧 `crates/text-document` 库，宿主不依赖文本解析实现。`npm run dev` 同时监听该库、插件及 SDK 的变化。

## 宿主浮层容器

声明 `capabilities` 含 `overlay` 的插件必须同时声明 `overlay` 尺寸，例如 `"overlay": { "width": 290, "height": 176, "anchor": "bottomRight" }`。宽高单位为 CSS 像素，指插件内容区（不含宿主 12px 的拖动条）；宽度范围 120–1600，高度范围 24–1200。`anchor` 可选，取 `topRight`（默认）、`topLeft`、`bottomRight`、`bottomLeft`，只决定面板首次出现的位置，用户拖动过以后以记住的位置为准。非浮层插件不能声明 overlay 尺寸。

宿主只提供两件事：一块可拖动的浮动面板，以及位置的保存与恢复。**面板里放什么完全由插件决定** —— 标题、关闭按钮、搜索框、纯信息文本都由插件自己画在 entry 网页里。宿主不提供标题栏、展开/收起按钮，也不提供位置重置按钮；在拖动条上双击可恢复默认位置。

这也是功能演进的硬边界：带有业务含义的控件必须画在插件浮层里，交互通过 `postTo()` / `onMessage()` 在同一插件的 view 与 panel 间同步。可复用的视觉规则进入 `sdk-ui.css`，状态和行为仍归插件。不要为了单个插件给宿主新增专用控件类型；只有不绑定格式、由插件提供文案与不透明结果的通用呈现原语才属于宿主。正常目标是发布新版插件包即可获得新能力，现有宿主无需升级。

确认类交互使用 SDK 的声明式模态通道：插件提供标题、说明、可选详情、按钮文案与不透明 action id，宿主只负责模态层、焦点、取消和把所选 id 返回插件。宿主不根据文案猜测动作，也不执行插件业务。这类通用原语与浮层容器遵循同一边界。

预览插件默认只读，目标是快速看见内容；为了兼容显示而生成的中间数据必须只存在于会话临时目录并随会话清理。若一个能力会持续修改、转换或替换用户内容，应作为独立插件和独立权限边界设计，不能悄悄扩进预览插件。

面板默认是关的，由插件用 `panel(true)` 打开；只有浮层的插件也可以直接用底部气泡开关。面板只在打开期间挂载，关闭即卸载，所以插件不要指望关掉以后还留着上次的状态。

同时声明 `view` 和 `overlay` 的插件是同一个 entry 挂载两次：主视口一次、浮层一次，`ready` 载荷里的 `role` 告诉网页自己是 `"view"` 还是 `"panel"`。

浮层这次挂载是**次要挂载**：它不能上报 `controls` 或 `status`，也不能发送 `presented`、`pending`、`fileChanged`、`returnView`、`mutate` —— 生命周期、变更声明和文档写入都属于视口。越权调用会被宿主明确拒绝，不会静默忽略。其余能力（`call`、`read`、`copy`、`setting`、`panel`、`peer`）两边都能用。文件信息插件仅负责内容排版，宿主没有针对它的尺寸分支。

## 主视口尺寸与沉浸模式

视口大小是**宿主的决定**，插件既拿不到也不需要开关：网页永远占满自己那个框，只有框在变。设置里的“沉浸模式”切换的就是这个框，与插件无关。

- **普通模式**：标题栏与功能栏是纵向布局里的两个 flex 项，各自占掉窗口的上下一条，插件视口正好是中间剩下的那一段 —— 两条栏在结构上不可能压住内容，宿主也不用猜它们有多高。这时视口有一条 1px 描边和 12px 圆角，四周露出窗口底色，读起来是一块独立内容区。
- **沉浸模式**：视口铺满整个窗口，两条栏改成贴在窗口上的浮层，平时隐藏，鼠标移到窗口四角那四个组件上才出现。

显形的规则完全属于宿主，判定区就是**每个气泡自己画出来的那个盒子**：左上品牌、右上窗口按钮、左下文件信息、右下工具栏里那些气泡（插件气泡与宿主按钮），指针进入任一个就露出两条栏，离开就收起。没有另画的感应区 —— 感应的范围就是气泡实际占的地方，所以它随文件名长短和气泡展开状态一起变，宿主不必维护第二套几何；反过来，不画东西的排布容器（右下那行气泡的 flex 容器）不算判定区，指针落在气泡之间的空隙上就是落在插件上。插件不能要求显形 —— 插件网页和它的浮层都是独立文档，浮层自己也有上下边缘，让浮层去驱动宿主的栏只会让栏在用户看不见的原因下忽隐忽现。

沉浸模式下两条栏**不接管自己画到的像素**：栏本身 `pointer-events: none`，只有里面的气泡（品牌、窗口按钮、文件信息、插件气泡、宿主按钮）吃指针。所以

- 气泡与气泡之间、栏与栏之间的空隙，指针直接落到插件上；
- 顶部那条整行拖拽区在沉浸模式下让出指针（拖窗口用品牌气泡，它本身就是拖拽把手）；
- 气泡既然就是判定区，未显形时它照样吃指针 —— 指针得能停在上面才叫得出两条栏，而进入的同一瞬间栏就显形了，点到的一定是已经看得见的气泡。窗口中间的像素始终属于插件。

这是刻意的取舍：**视口是插件唯一需要理解的矩形**。滚动条轨道、选区、视觉边缘都长在那个矩形上，沉浸模式只是把矩形变成整个窗口，插件不必为两种模式写任何分支。宿主自己的浮层也画在同一个矩形里，所以浮层同样不会被两条栏或视口边界裁掉 —— 位置仍然由宿主决定，插件决定浮层里画什么。

视口矩形**从边到边都是插件的像素**，宿主不在这块矩形里画任何东西（归属规则见 [界面归属](specs/plugin-capabilities.md)），所以它也没有上下渐隐：贴到边缘的内容就是它本来的样子，想柔和边缘就自己画。宿主早先那层边缘渐变已经去掉 —— 除了它本来就压在插件画面上，换到亮色主题还会变成一条压在画面上的白边。安全距离只为浮动栏留位（沉浸模式下即栏高），插件不必为此另造数值；换肤下发的是颜色与形状 token，不含它（插件网页是独立文档，读不到宿主变量）。

### 浮层置顶：宿主浮层与渲染内容的层级契约

**宿主保证**：两条栏（以及栏里的气泡）和插件浮层永远画在插件渲染内容之上，插件无法用任何渲染手段把宿主浮层盖住或顶掉。这是「视口是插件唯一需要理解的矩形」的另一半 —— 矩形里面归插件画，矩形的边框、按钮和浮层归宿主，两者互不影响。所以：

- 插件可以自由铺满视口，不必为两条栏预留任何位置；
- 四角那四个气泡属于宿主：指针进入即显形两条栏，落在气泡上的指针与点击不转发给插件。插件不因此损失任何交互——视口里只有渲染内容，功能操作都在工具栏和浮层里（见 [界面归属](specs/plugin-capabilities.md)），所以这几块像素归宿主不会拿走插件必需的东西；
- 插件浮层画在上述所有内容之上，位置由宿主决定。

**插件侧的义务**：渲染内容必须留在**页面合成**里。WebView2 会把一部分渲染单独提升成系统合成平面（正在播放的 `<video>` 是最常见的一种，其它加速渲染同理），这类平面一旦脱离页面层序就会盖住宿主浮层；而命中测试不受影响，症状因此极具欺骗性：按钮点得到、`title` tooltip 弹得出，画面却看不见 —— 只要有一个与它重叠的浮层出现，Chromium 回到正常路径，宿主浮层又立刻回来。

**做法**：让被提升的那块 quad 不具备提升资格，视觉上不可见即可：

```css
video { border-radius: 1px; clip-path: inset(0); }
```

`tests/host-chrome.test.mjs` 会检查这条契约：宿主浮层的层级、隐藏时不吃指针，以及任何带 `<video>` 的插件包是否写了退出样式。

**判定方法**：命中测试与 tooltip 正常而画面缺失时，先怀疑合成路径，而不是「谁压谁」的 CSS 层序。注意 CDP 的 `Page.captureScreenshot` 截的是渲染器的合成结果，**看不到系统合成平面**，这类故障在它眼里可能一切正常，只能用真实屏幕截图判断。

## 文本组件与位置共享

文本预览、代码预览、Markdown 预览及文本编辑均使用插件侧共享文本组件。完整说明与手动验收见 [文本插件族](specs/text-plugins.md)。`fileNames` 补充无扩展名匹配；`viewState()` 提供按文件与契约隔离的不透明阅读状态，保存后重新创建会话也可恢复。

安全距离在功能栏显隐时保持稳定，只随模式、栏尺寸及窗口布局变化更新。`onTheme()` 可用于触发组件重新测量。共享文本组件同时设置滚动定位的安全边界；Markdown 正文与大纲复用相同变量，图片适应窗口使用扣除安全距离后的区域。

## 市场来源与安装交互

分成三层，各自的职责不重叠：

| 层 | 是什么 | 对应的动作 |
|---|---|---|
| 宿主 | 只有外壳，没有任何预览实现，也不打包任何插件 | 解析插件源、校验、安装、运行 |
| 插件源 | 一份远程目录 `catalog.json`，列出有哪些插件、当前是哪个构建 | 插件信息获取 |
| 包链接 | 目录条目里的 artifact，指向源基地址下的一个 zip | 插件下载 |

所以一个刚装好的应用**预览不了任何东西**，直到用户从插件源装了插件。首次启动会打开一次引导页（见下），之后一切增删都在“插件管理 → 插件市场”里。

### 插件源

宿主从 `src-tauri/plugin-sources.json` 读取来源列表，发行版把它作为资源随应用提供：

```json
{
  "api": 1,
  "sources": [
    {
      "name": "Ember Peek",
      "catalog": "https://YOUR_BUCKET.oss-cn-hongkong.aliyuncs.com/ember-peek/channels/stable/api-1/windows-x86_64/catalog.json",
      "base": "https://YOUR_BUCKET.oss-cn-hongkong.aliyuncs.com/ember-peek/packages/windows-x86_64/"
    }
  ]
}
```

- `catalog` 读目录，`base` 用来拼 artifact 名。两者都必须是 http(s) 地址、`file://` 或绝对路径；**相对路径会被拒绝**，因为它只能相对于宿主进程的工作目录解析，那不是任何镜像能依赖的位置。
- 最多 8 个源。同一个插件出现在多个源里时，哈希相同就是同一个包的镜像，安装按顺序回退，先前失败的镜像不影响安装；哈希不同则视为冲突，保留第一个并在界面报告。
- 远程目录缓存 10 分钟，本地镜像缓存 1 秒；首启重试与市场刷新可以绕过缓存，超时 8 秒。读取失败的源沿用上一次成功的结果，并在界面列出原因。
- 改配置不需要改代码：`EMBER_MARKET_SOURCES` 指向另一个来源文件即可（开发时用来验证真实的远程源）。
- `name` 是**配置数据**，按作者写的样子显示，宿主不翻译它。唯一的例外是开发环境那个本地镜像：它是宿主自己起的名字，所以按界面语言显示（英文界面下是 "Development mirror"），切语言时跟着变。

### 首次启动引导页

应用是外壳，所以首次启动会打开一次引导页：列出插件源里标了 `recommended` 的插件（一个都没标则取列表前几项），让用户勾选安装，而不是把整份目录铺开。勾中的**走与市场完全相同的公开安装流程**（`market_prepare` 下载校验 → `install_plugin` 复制），宿主不会因为“这是首次启动”而走任何特殊路径。

页面给三条出路，按这个顺序排：**安装所选**（装勾中的推荐项，然后进入应用）、**去插件市场**（不装推荐项，直接去挑）、**稍后再说**（什么都不做，窗口让位，应用留在托盘）。来源推荐的那几个都已经装好时，页面不再摆出目录里其他条目来凑数，而是说明情况并让用户走「去插件市场」——所以不需要为“全都装完了”单独做一套页面。

已经装上的插件不会出现在引导页的可选列表里（引导页过滤的是"这次能装什么"）。宿主不记录用户卸载过什么，所以卸载过的插件如果仍被来源标为推荐，下次重置为首次启动时还会被建议；答案记录在 `host-state.json` 的 `onboarded` 字段中，因此引导页只出现一次，即便当时不装，之后也能在插件市场里装。

出现原因也如实显示：插件源读不到、条目不可用、平台不匹配，都会在引导页里列出来，而不是显示成一个空的列表。单个插件安装失败不会中断其余插件，失败项单独列出。

### 平台声明

`targets` 声明这个包的原生程序能跑在哪些 `系统-架构`（如 `windows-x86_64`，最多 8 项，小写）。省略表示不限制，因此 `targets` 出现之前构建的包照常加载。打包脚本按当前构建主机自动写入这一项，并把它算进 `buildId`——同一份源码在 Windows 和 macOS 上构建出来是两个不同的包。

市场的处理是：条目声明的平台不含当前主机就不展示，并给出说明；`prepare` 会再拒绝一次；解包后还会用包内清单的 `targets` 复核一次。三层都用同一份声明，所以一个 Windows 包不会被误装到别的平台上，直到启动程序才失败。

### 发布：目录与包格式

`npm run plugins:dist` 产出可直接上传的发布物（`--dist` 隐含 release 构建，不会把 debug 可执行文件发出去）：

```text
.release/catalog.json                              供插件源读取的目录索引
.release/ember.text-0.1.0-<buildId24>.zip          每个插件一个包
```

官方发布使用 `plugins:validate` → `plugins:plan` → `plugins:publish`，先上传并校验包，最后切换 OSS 目录。包名按 `id-版本-buildId` 内容寻址，线上历史包不会被清理。同版本、同源码指纹重编译时复用最初发布的包，源码输入变化必须升版本。真实地址由 `source:configure` 配置，详见 [OSS 分发](oss-distribution.md)。本地 `plugins:build` 与 `plugins:dist` 仍会清理各自输出目录里的陈旧包，后者不会写开发镜像。

包是 **zip**，`plugin.json` 位于压缩包根目录，其余条目是相对路径：

```text
plugin.json
bin/your-plugin.exe
ui/index.html
ui/view.js
ui/sdk.js                 每个包都有
ui/sdk-*.css  ui/sdk-*.js 按插件实际引用到的共享文件
```

压缩包里的 `plugin.json` 把安装期才赋值的 `revision` 写成 `0`，因此同样的输入总是产生同样的字节，目录里的 `sha256` 才有意义（安装时由安装器自己分配 `revision`）。条目名必须是普通相对路径：反斜杠、盘符、绝对路径和 `..` 一律拒绝，符号链接在解包时同样拒绝；声明的解压总量与**实际写出**的字节数都会受上限约束。这些拒绝发生在写入任何文件之前。

目录的每个条目自带 `version`、`buildId`、`sha256`、`size` 和界面需要的展示字段，所以市场卡片不必先下载就能显示版本、图标与扩展名。

上面那句“同样的输入总是产生同样的字节”只覆盖打包这一步：`buildId` 把可执行文件的字节也算进去，而链接器会在 PE 头里写链接时刻的时间戳（以及由它派生的调试标识），所以**源码没动、重新构建一次，可执行文件与 `buildId` 都会变**。要让同一份源码始终得到同一个 `buildId`，可以在链接参数里加 `/Brepro`（时间戳改为由输入内容的哈希得出）。

`buildId` 与 `version` 分工明确，别混用：`buildId` 是机械身份——判断“这是不是同一个包”、给发布物命名、开发环境据此决定要不要重装；**`version` 决定用户看到什么**，只有远端 SemVer 版本更高时市场才会对已装用户提示“有更新”。所以没升版本号就重新发布，老用户不会被提示，要发布就得升版本。开发环境不受这条影响：那里的同步看的是字节，改完插件代码不升版本也会立刻装进本地实例。

其中 条目里的 `i18n` 是同一份语言的展示文案：`name` 来自插件的 `plugin.json`，`summary` 来自插件源码目录的 `listing.json`，打包时汇总进目录。市场卡片按读取方的界面语言显示，条目没声明的语言回落到条目自带的基础字段 —— 所以一份老目录在英文宿主上也不会变得没有名字。

`recommended` 表示“适合首次安装”：首启引导页只列出这些条目，其余留在插件市场里。它来自插件源码目录的 `listing.json`（和 `summary`、`publisher` 写在一起），所以宿主不硬编码任何插件 id——换插件源或换一批推荐项都不需要改代码。一个源什么都没标时，引导页取列表里的前几项，而不是把整份目录铺开。

### 校验边界

下载后校验两件事，各自回答不同的问题：

- `sha256` 对应**传输**：拿到的字节就是目录索引的那个文件。校验在解包前完成，因此被替换的包不会有机会落盘。
- `buildId` 对应**身份**：解包后的清单声明的构建与目录索引的是同一次构建。字节完整但装错了包（例如目录索引 A、镜像给了 B）会在这里被拒绝。

**`buildId` 不等于签名。** 它由打包脚本从内容算出，宿主只能核对"包内声明 == 目录声明"，无法重算它证明内容与指纹一致。目录本身若可被替换，这套校验就失去意义，所以：

- 签名接口已经预留：目录可以声明 `signature`。**当前版本没有实现校验，因此声明了签名的目录会被直接拒绝**，而不是被当作已校验。未签名的目录是当前信任模型的诚实表述，签名在发布签名工作落地时接管这里。
- 装进来的原生程序与用户同权限，没有 OS 级沙箱，所以第三方来源应视为与手动安装程序等价：市场会展示真实来源地址和大小，用户点击才算确认。

下载物按 `sha256` 缓存（开发 `.plugin-cache`，发行版在应用数据目录的 `plugin-cache`），重复安装不重复下载；缓存内容与目录记录不符时会被丢弃并重新下载。缓存只保留磁盘上仍在用的构建（见[安装与验收](#安装与验收)），卸载后对应条目也会清掉。

### 开发时的市场

开发环境不读发行版那份来源文件，而是把最近一次插件构建结果当作本地镜像（`.marketplace/`，`plugins:build` 与监视器持续重建它），因此插件源码一改，镜像里就出现新构建，安装走的是与线上完全相同的 zip 下载与校验路径。开发环境**故意不读官方源**：本地构建比已发布的更新，优先用已发布的话开发循环会装到旧包。

本地镜像缓存 1 秒，开发宿主每 2 秒检查一次；构建完成后通常下次同步即可发现。若有未保存草稿，更新会被拒绝。远程目录缓存仍是 10 分钟，可在市场主动刷新。

需要验证真实远程源时，用 `EMBER_MARKET_SOURCES` 指向一个来源文件即可（它只在 debug 构建里生效）。

窗口是按需创建的，托盘应用启动时通常一个窗口都没有。调试时如果需要窗口（例如让 `tools/live-targets.mjs` 有目标可连），用 `EMBER_DEBUG_WINDOW=settings|plugins|about|welcome` 让宿主启动时直接打开对应页面，而不是去清掉首启引导的答案——后者会让下次启动重新弹出引导页。同样是 debug 构建专有。

### 数值拖动工具栏控件

`controls()` 支持 `kind: "scrub"`：声明有限的 `value`、`min`、`max`（`0 < min < max`，`value` 必须在区间内），可选 `suffix`（≤8 字）。静止时只有居中的数值；**指针悬停**（或键盘聚焦、或正在拖动）时数值左移、右侧滑入标尺与指示块，离开或松手后两侧动画回到居中——数值始终可读，而且悬停就把"这个数字可以拖"讲清楚了。指示块的位置＝数值在 `min`–`max` 里的位置，所以读数和轨道永远一致：12% 的音量就停在轨道的 12%。拖动方向向上增大、向下减小。拖动本身是**指数**变化、比值恒定：约 40px 位移对应一次 e 倍，所以 1–100 的音量全程约 180px、2–2000 的缩放约 270px，跨几个数量级也不会一拖就飞或拖不到头——因此跨数量级的控件要把 `min` 收到真正用得到的范围，否则轨道会在低端占满、高端几乎不动。`run(value)` 接收绝对数值，不是增量；插件重新发布控件以同步滚轮等操作引起的变化。键盘方向键按 ×1.1 递增、反向键除以 1.1，Home 到 `min`、End 到 `max`——这里的步进与设置项的 `step` 无关。图片插件以百分比声明缩放范围，并保留适应窗口和原始尺寸按钮。
