# 发布说明规范

发布说明回答“用户从正在使用的公开版本升级，会得到什么变化”。开发记录回答“开发过程中做了什么、发现什么、如何验证”。两者不能直接互相搬运。

## 比较基准

整理发布说明前，核对公开 Release、对应 Git 标签与实际交付的插件版本。只有用户已经获得的版本才是比较基准；上一提交、PR、开发分支、计划发布章节或本地 buildId 都不能代替它。宿主与插件独立发布时分别确认基准，不能因为插件源码发生过修改，就认定用户已经使用过那个修改版本。

当前 0.1.1 发布说明以公开的 0.1.0 为基准。这只是当前例子，后续发布必须重新核对，不得永久使用 0.1.0。已有公开发布正文不为开发过程重新改写；尚未发布的版本章节可继续整理。

## 条目分类

| 分类 | 可以写什么 | 不能混入什么 |
| --- | --- | --- |
| Added | 用户旧版本没有、此次首次交付的最终能力 | 新功能开发期间每一步新增 |
| Changed | 用户已使用功能的行为、默认值或体验变化 | 首发功能未发布中间版本的界面改版 |
| Fixed | 用户已发布版本中存在的问题及其改善结果 | 首发功能开发中发现并修好的错误、回归或性能问题 |
| Unreleased 开发记录 | 实现方案、开发错误与修复、技术预算、测试和复现过程 | 将这些内容原样作为面向用户的发布正文 |

首次发布音频插件时，发布条目描述最终的波形、播放、跳转与倍速能力。开发时出现过的倍速显示 0×、滚轮回跳、加载动画不满意，留在开发记录，不能写成用户旧版音频插件的修复，因为用户旧版没有这个插件。

首次发布模型或办公插件同理：样条线回退、文档背景兼容和新缩略图侧栏闪烁等开发问题，不能作为面向旧版用户的修复。已发布 PDF 的大文件读取问题则需要核对其在用户基准版本中的代码、实际复现或用户报告，确认后才能写入 Fixed。

## 发布前审核

1. 写明本次比较的公开宿主版本、标签，以及涉及插件的已发布版本；根据发布工件、发行源码或用户报告核对变化。
2. 逐条判断该功能或问题是否存在于用户基准版本。无法确认的修复留在开发记录，核实后再分类；提交标题或测试名包含“fix”不能作为证明。
3. 同一首发功能合并为最终能力描述，去掉研发中的前后改版、试验、参数预算、测试数量和性能测量过程。
4. 检查 Changed 是否确实改变了用户已有功能，Fixed 是否确实影响了已发布用户版本；技术步骤留在开发区。
5. 使用发布日志提取脚本预览最终正文，检查它只包含面向用户的变化，再运行文档链接与发布日志测试。

根目录 [CHANGELOG](../CHANGELOG.md) 的具体版本章节是发布正文来源；[贡献指南](../CONTRIBUTING.md)和 [AGENTS.md](../AGENTS.md)共同约束本规则。文案语义需要人工核对，自动测试不能判断某个开发问题是否曾交付给用户。
